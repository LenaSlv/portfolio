# AGENTS.md

Этот файл — руководство для Codex при работе в этом репозитории.

## О проекте

Репозиторий — портфолио UX/UI-дизайнера. Текущая цель: сделать сайт-портфолио и опубликовать его на GitHub Pages. Основной кейс: мобильное приложение заказа корпоративного транспорта для сотрудников крупного банка (iOS/Android, внутренний продукт под NDA).

Язык всех материалов — русский. Отвечать и писать тексты на русском.

## Структура

- `docs/` — исходные рабочие материалы двух кейсов. **Файлы в `docs/` сейчас не редактировать** — это источник контента для сайта, правки в них вносит только владелец портфолио.
- `docs/корпоративный-транспорт/` — материалы основного кейса под NDA:
  - `01_кейс_финальный_текст.md` — финальный текст для публикации
  - `02_чеклист_публикации.md` — чек-лист макетов и страницы кейса
  - `03_подготовка_к_собеседованию.md` — заготовки ответов для собеседования
  - `04_полные_материалы_кейса.md` — полные рабочие материалы
  - `05_черновик_структуры_кейса.md` — черновик новой структуры
- `docs/транспорт-калининграда/` — материалы самостоятельной транспортной концепции:
  - `01_полные_материалы_кейса.md` — полные рабочие материалы
  - `02_предложение_по_структуре_кейса.md` — предложение по структуре публикации
- `index.html` и `styles.css` — опубликованная страница основного кейса.
- `case-transport-pet.html` и `styles-pet.css` — страница транспортной концепции.
- `case-corporate-draft.html` — черновая версия структуры основного кейса, закрытая от индексации.

## Сайт-портфолио

- Хостинг: GitHub Pages. Стек и структура сайта — по мере разработки (пока не зафиксированы).
- Контент страниц кейса берётся из `docs/` дословно, без пересказа и «улучшения» формулировок.
- Тексты не усложнять: не переписывать простые формулировки в более «сложные» и наукообразные.

## Критические ограничения (NDA)

- Название заказчика и продукта не раскрываются. Допустимая формулировка масштаба: «внутренний продукт для крупного банка».
- Все данные на экранах и в текстах — вымышленные: имена, номера автобусов, адреса, названия остановок, табельные номера. При редактировании не добавлять ничего похожего на реальные данные.
- В шапке кейса обязательны: заголовок, «Внутренний продукт для крупного банка · NDA», роль, платформа, пометка «экраны показаны с вымышленными данными».

## Конвенции текста кейса

- Тон: спокойный, продуктовый, без оправданий за NDA. Каждое дизайн-решение объясняется через ценность для пользователя И для бизнеса.
- Заголовки блоков — без точек в конце («Предварительный заказ», не «Предварительный заказ.»).
- Терминология едина в тексте и на макетах (пример открытого вопроса: «Табельный №» vs «Номер сотрудника» — см. чек-лист).
- «Прибытие через N мин», не «Отправление» (экран закреплённого маршрута).
- Плейсхолдеры экранов оформляются курсивом: `*[Экран: описание]*`.
- Финальная строка кейса: «Детали проекта и остальные сценарии могу показать и рассказать на встрече».

## Ключевые формулировки (не искажать при правках)

- Два сценария проектировались «как один путь»: предзаказ → закрепление за маршрутом; общие элементы (карта, карточка поездки, QR); при переходе пользователь не переучивается.
- Механика закрепления была в требованиях — не присваивать её как авторское решение. Авторское: связность двух сценариев, иерархия экрана закреплённого маршрута, структура сбора обращений («данные вместо свободного текста»).
- QR-код привязан к учётной записи и автоматически обновляется — пересланный скриншот недействителен.

## Типовые задачи

- Разработка сайта-портфолио: вёрстка страниц, перенос контента кейса из `docs/` на сайт.
- Сверка страниц сайта с текстом кейса и чек-листом публикации — сайт не должен противоречить `docs/`.
- Редактуру самих файлов `docs/` не выполнять, пока владелец не снимет запрет (см. «Структура»).

## Работа с файлами через MCP WebStorm

- Для чтения, поиска, создания и редактирования файлов проекта использовать MCP-сервер WebStorm. Во всех вызовах передавать `projectPath: C:\Users\user\WebstormProjects\portfolio`, если инструмент поддерживает этот параметр.
- HTML- и CSS-файлы редактировать через MCP WebStorm: сначала прочитать актуальное содержимое, затем внести адресную правку и проверить результат. Не использовать для этих изменений прямую запись через shell или другие обходные способы.
- Для поиска использовать инструменты поиска MCP WebStorm, для чтения — `read_file`, для адресной замены — `replace_text_in_file`. После изменений HTML или CSS запускать сборку либо доступную проверку проекта через WebStorm MCP.
- Файлы в `docs/` не изменять даже через MCP WebStorm — для них действует запрет из раздела «Структура».

## Визуальная проверка через Chrome

- После правок HTML, CSS или JS прогонять страницу в QA-профиле Chrome на desktop и на мобильном viewport `390 × 844`.
- В расширении `chrome-qa-extension` использовать кнопку «Собрать комплект»: она сохраняет PNG и JSON с одним идентификатором проверки.
- Проверять в JSON горизонтальное переполнение и список проблемных элементов, а PNG просматривать визуально до завершения задачи.
- При найденном расхождении сначала исправлять код, затем повторять проверку и обновлять комплект скриншота и отчёта.
